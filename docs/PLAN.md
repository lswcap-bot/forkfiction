# ForkFiction(포크픽션) — 포크할 수 있는 소설 플랫폼 기획서

## 서비스 정의와 핵심 개념

**ForkFiction(포크픽션)은** 원작 소설을 장 단위로 올리면, 누구나 원하는 장에서 갈라져 나와 자기 버전을 이어 쓸 수 있는 소설 플랫폼이다. 위키처럼 정답 하나로 모으는 구조가 아니라, 깃허브처럼 원작은 그대로 두고 갈래가 나무처럼 뻗어 나가는 구조다.

한 줄 소개: "이 이야기, 여기서부터 당신 버전으로."

| 개념 | 뜻 | 깃허브에 빗대면 |
| --- | --- | --- |
| 원작 | 작가가 처음 올린 작품. 장(章)들의 묶음 | 원본 저장소 |
| 갈래(포크) | 원작의 특정 장에서 갈라져 나온 새 버전. 갈라진 장 이전은 원작을 그대로 물려받는다 | 포크 + 브랜치 |
| 갈림점 | 갈래가 원작과 달라지기 시작한 장 | 분기 커밋 |
| 고쳐 쓰기 기록 | 한 장의 수정 이력 | 커밋 히스토리 |
| 계보 | 이 갈래가 어디서 왔는지 거슬러 올라가는 경로. 모든 갈래 화면에 자동 표기 | 포크 출처 표시 |
| 갈래 지도 | 한 원작에서 뻗어 나간 모든 갈래를 나무 모양으로 보여 주는 화면. 서비스의 대표 화면 | 네트워크 그래프 |
| 정사 인정 | 원작자가 마음에 드는 갈래에 붙여 주는 배지 | 공식 머지 대신 쓰는 장치 |

(그림: 갈래 지도 예시 — 가로축은 장 번호. 원작은 1~10장 굵은 줄, '단이의 마을'은 6장에서, '울라의 길'은 8장에서 갈라지고, 그 갈래에서 10장에 다시 갈래의 갈래가 나온다. 갈림점 앞의 장은 복사하지 않고 원작을 가리킨다.)

그림의 갈래 제목은 설명을 위한 가상 예시다. 울라의 길은 1\~7장을 원작에서 물려받고 8장부터 달라지며, 그 갈래에서 다시 갈라진 갈래도 뿌리 원작까지 계보가 이어진다.

이 서비스는 갈래를 원작에 다시 합치는 '머지' 기능을 MVP에서 다루지 않는다. 소설은 코드와 달리 두 버전을 합치는 일이 드물고, 원작자에게 부담만 주기 때문이다. 대신 '정사 인정' 배지로 원작자와 갈래 작가를 잇는다.

첫 시드 콘텐츠는 『칼의 여행』 1\~10장이다. 원작이 장 단위로 끝맺음이 분명하고, 떠난 동료(갈기·아르샤·단이·울라·진아)마다 '그 뒤 이야기' 갈래가 나오기 좋은 구조다.

## 사용자와 핵심 시나리오

사용자는 원작자, 갈래 작가, 독자 세 부류다. 한 사람이 세 역할을 모두 할 수 있다.

| 사용자 | 원하는 것 | 막히는 지점 |
| --- | --- | --- |
| 원작자 | 내 이야기가 퍼지고, 내가 원작자라는 사실이 끝까지 남는 것 | 포크가 원작을 가릴까, 출처 없이 베낄까 불안 |
| 갈래 작가 | 좋아하는 이야기를 내 식으로 이어 쓰고 읽히는 것 | 처음부터 다 쓰기는 부담, 어디서 갈라져야 할지 막막함 |
| 독자 | 한 이야기의 여러 결말을 골라 읽는 것 | 갈래가 많아지면 뭘 읽어야 할지 모름 |

**시나리오 A — 원작 올리기.** 원작자가 구글 계정으로 로그인해 MD 파일을 올린다. 시스템이 `#` 제목 기준으로 장을 나눠 보여 주고, 원작자는 장 순서와 제목을 확인한 뒤 라이선스와 '갈래 허용'을 고르고 공개한다.

**시나리오 B — 갈래 내기.** 독자가 『칼의 여행』 8장을 읽다가 "울라가 강무열을 따라가지 않았다면?"이라고 생각한다. 8장의 '여기서 갈라지기' 버튼을 누르면, 1\~7장은 원작을 물려받고 8장부터 편집 가능한 새 갈래가 생긴다. 새 갈래에는 '『칼의 여행』 8장에서 갈라짐'이라는 계보가 자동으로 붙는다.

**시나리오 C — 갈래 골라 읽기.** 독자가 원작의 갈래 지도를 연다. 어느 장에서 갈래가 많이 갈라졌는지, 어느 갈래가 별을 많이 받았는지, 원작자가 정사로 인정한 갈래는 무엇인지 한눈에 보고 골라 읽는다.

**시나리오 D — 달라진 곳 비교.** 독자나 원작자가 갈래의 어느 장을 열고 '원작과 비교'를 누른다. 바뀐 문단이 양쪽에 나란히 강조돼 보인다.

**시나리오 E — 정사 인정.** 원작자가 알림으로 새 갈래를 확인하고, 마음에 드는 갈래에 '정사' 배지를 붙인다. 배지가 붙은 갈래는 갈래 지도와 원작 첫 화면에서 위쪽에 노출된다.

## MVP 범위

MVP의 목표는 "사람들이 실제로 갈래를 내는가"를 확인하는 것이다. 그래서 올리기 → 읽기 → 갈라지기 → 고쳐 쓰기 → 갈래 지도까지 한 바퀴만 돌게 만든다.

| 구분 | MVP에 넣는다 | 나중으로 미룬다 |
| --- | --- | --- |
| 계정 | 구글 로그인, 필명·소개 프로필 | 카카오·네이버 로그인, 팔로우 |
| 작품 올리기 | MD 파일 업로드·붙여넣기, 장 자동 분할, 표지 없이 글만 | 표지 이미지, 삽화, docx 가져오기 |
| 읽기 | 장별 읽기 화면, 이전·다음 장, 글자 크기 | 읽던 위치 기억, 오프라인 읽기 |
| 갈라지기 | 원하는 장에서 포크, 계보 자동 표기, 갈래의 갈래 | 원작으로 되돌리는 머지 제안 |
| 고쳐 쓰기 | 장 편집기(MD), 장 추가·삭제·순서 변경, 저장할 때마다 수정 기록 | 여러 사람 동시 편집 |
| 비교 | 갈래의 장과 원작 장을 문단 단위로 나란히 비교 | 임의의 두 갈래 비교 |
| 갈래 지도 | 원작 하나의 갈래를 나무 모양으로 표시, 누르면 이동 | 확대·축소, 필터 |
| 발견 | 별(좋아요), 최신순·별점순 목록, 정사 배지 | 추천 알고리즘, 태그, 검색 |
| 알림 | 내 작품에서 새 갈래가 생기면 사이트 안 알림 | 이메일·푸시 알림 |
| 운영 | 신고 버튼, 관리자 숨김 처리, 라이선스 표기, 구글 애드센스 광고 자리(F10) | 수익 배분, 유료 연재 |
| AI | 없음(사용자가 밖에서 AI로 쓴 글을 올리는 것은 허용) | 'AI 갈래 도우미' — 갈림점과 방향만 주면 초고를 써 주는 기능 |
| 기기 | 모바일에서도 읽기·갈래 지도 가능(반응형 웹) | 앱 |

AI 갈래 도우미는 차별점이 될 기능이지만 MVP에서는 뺀다. API 비용이 들고, 성의 없는 갈래가 쏟아지는 문제를 먼저 풀어야 하기 때문이다. 사람이 쓴 갈래가 실제로 나오는지 본 뒤 2단계에서 붙인다.

## 기능 명세

서비스의 심장은 F3 갈라지기다. 갈래는 장 본문을 복사하지 않고 원작의 '수정본'을 가리키다가, 고칠 때만 새 수정본을 만드는 방식(copy-on-write)으로 설계한다. 저장 공간을 아끼고, 어느 장을 물려받았고 어느 장을 고쳤는지가 데이터에 그대로 남는다.

**F1. 로그인과 프로필**

- 구글 로그인. 처음 로그인하면 필명(중복 불가, 영문·숫자)과 표시 이름을 정하고, 이용약관·개인정보 처리방침에 동의한다. 동의하지 않으면 읽기만 할 수 있다.
- 프로필 화면에 내 원작, 내 갈래, 받은 별 수를 보여 준다.

**F2. 작품 올리기**

- 로그인하고 약관에 동의한 사용자만 올릴 수 있다. .md 파일 업로드 또는 본문 붙여넣기.
- 장 분할 규칙: 맨 위 `#` 제목이 하나면 작품 제목, 그 아래 `##`를 장으로 본다. `#`이 여러 개면 각 `#`을 장으로 보되, 맨 위 `#` 아래에 본문이 없으면(바로 다음 `#`이 오면) 그 `#`은 작품 제목으로 본다. 장 제목 앞의 'N장 — '은 장 번호와 겹치므로 뗀다. 첫 장 앞의 글은 '머리말' 장이 된다. 분할 결과를 미리보기로 보여 주고 제목·순서를 고치거나 장을 지울 수 있게 한다(서문·작가의 말 빼기).
- 작품 주소: 제목을 로마자로 바꿔 채우고 작가가 고칠 수 있다. 겹치면 -2, -3을 붙이고, 저장 전에 최종 주소를 보여 준다. 주소는 임시 저장 동안에만 바꿀 수 있고 한 번 공개하면 바꿀 수 없다(`first_published_at`).
- 입력 항목: 제목, 소개(300자), 라이선스(기본 CC BY-SA 4.0), 갈래 허용 여부, AI 활용 여부(없음 / 일부 / 대부분).
- 장르 구분은 두지 않는다(웹소설 전반). 임시 저장 후 공개. 비공개 작품은 본인만 본다.

**F3. 갈라지기(포크)**

- 갈래 허용인 작품의 모든 장 끝에 '여기서 갈라지기' 버튼. 로그인해야 누를 수 있다.
- N장에서 갈라지면: 1\~(N−1)장은 원작의 그 시점 수정본을 가리키는 '물려받은 장', N장은 원작 본문을 초안으로 담은 '고칠 장', N+1장 이후는 가져오지 않는다(갈래 작가가 새로 쓴다).
- 물려받은 장은 갈라진 시점의 수정본에 고정한다. 원작자가 나중에 3장을 고쳐도 갈래의 3장은 그대로다. (원작이 바뀌었다는 안내는 2단계.)
- 물려받은 장을 고치려 하면 "이 장부터 달라집니다" 경고 후 고칠 수 있게 한다. 갈림점은 '처음으로 달라진 장'으로 자동 갱신한다.
- 갈래도 다시 갈래를 낼 수 있다. 모든 갈래는 뿌리 원작을 기억한다.
- 갈래 대문에 계보를 항상 표시한다: 『칼의 여행』(이석원) → 8장에서 → 『울라의 길』(아무개). 갈래 작가가 지울 수 없다.
- 갈래 만들 때 한 줄 갈래 소개("울라가 떠나지 않았다면")를 필수로 적는다. 갈래 지도에 이 문장이 보인다.

**F4. 고쳐 쓰기**

- 장 단위 MD 편집기(왜쪽 쓰기, 오른쪽 미리보기, 모바일에서는 탭 전환).
- 저장할 때마다 수정본 하나가 쌓이고, 선택으로 한 줄 메모를 남긴다. 자동 저장은 브라우저 임시 보관만 하고 수정본은 만들지 않는다.
- 장 추가, 삭제, 순서 변경. 물려받은 장을 삭제하면 그 장이 갈림점이 된다.
- 장별 수정 기록 보기와 이전 수정본으로 되돌리기.

**F5. 원작과 비교**

- 갈래의 고친 장에서 '원작과 비교'. 비교 대상은 그 장이 처음 가져온 원작 수정본이다.
- 문단 단위로 나란히 보여 주고, 바뀐 문장을 색으로 표시한다. 새로 쓴 장은 '원작에 없는 장'으로 표시한다.

**F6. 갈래 지도**

- 원작 화면의 탭 하나. 가로축은 장 번호, 원작은 굵은 줄 하나, 갈래는 갈림점에서 뻗어 나간 가지로 그린다.
- 가지마다 제목, 작가, 별 수, 한 줄 소개. 정사 배지는 강조색. 누르면 그 갈래로 이동.
- 장별로 '여기서 갈라진 갈래 N개'를 표시해, 독자가 가장 많이 갈라진 장을 알 수 있게 한다.
- 가지가 50개를 넘으면 별 상위 순으로 자르고 '더 보기'로 목록을 보여 준다.

**F7. 발견과 반응**

- 홈: 새 원작, 요즘 갈래가 많이 나는 원작, 별이 많은 갈래.
- 별(좋아요)은 작품 단위로 한 사람당 한 번.
- 정사 인정: 뿌리 원작자만 붙이고 뗄 수 있다.

**F8. 알림**

- 내 작품에서 새 갈래가 공개되면, 내 갈래가 별을 받거나 정사로 인정되면 사이트 안 알림(종 아이콘).
- 새 갈래 알림은 갈래를 만들 때가 아니라 **갈래가 처음 공개될 때** 보낸다. 갈래는 임시 저장 상태로 만들어지므로, 만들 때 알리면 원작자가 아직 읽을 수 없는 갈래를 알림으로 받게 된다. 자기 작품에서 갈라진 갈래는 알리지 않는다. (2단계에서 결정, 4단계에서 반영)

**F9. 신고와 관리**

- 작품·갈래마다 신고 버튼(표절, 불법 콘텐츠, 음란·폭력, 기타).
- 관리자 화면에서 신고 목록 확인, 숨김·복구.

**F10. 광고(초기 수익 모델)**

- 초기 수익은 구글 애드센스 광고로 낸다. 광고 수익은 운영자에게 귀속되며, 이 점을 약관에 적는다. 작가 수익 배분은 2단계 이후에 검토한다.
- 광고는 모두 공통 컴포넌트 `<AdSlot id="..." />` 하나로 넣는다. 자리 크기를 미리 잡아 두어 광고가 늦게 뜨거나 안 떠도 본문이 출렁이지 않게 한다.
- 애드센스 승인 전에는 회색 자리표시만 보이고, 환경 변수 하나로 광고를 켜고 끈다.
- 애드센스는 승인 심사가 있다. 원본 콘텐츠가 어느 정도 쌓이고 개인정보 처리방침 페이지가 생긴 뒤 신청하고, ads.txt 등 세부 요건은 신청 시점의 구글 안내를 따른다.

| 화면 | 광고 자리 | 이유 |
| --- | --- | --- |
| 장 읽기 | 본문 끝, '다음 장'과 '여기서 갈라지기' 버튼 사이 1개. 긴 장은 본문 중간 문단 경계에 1개 추가. 넓은 화면에서는 오른쪽 여백 1개 | 페이지뷰가 가장 많은 화면. 문장 한가운데는 피한다 |
| 홈 | 작품 카드 목록 사이(일정 간격) | 목록에 자연스럽게 섞임 |
| 작품 대문 | 장 목록 아래 1개 | 읽기 시작 전 흐름을 끊지 않음 |
| 갈래 지도 | 지도 아래 1개 | 지도 조작을 가리지 않음 |
| 프로필 | 목록 아래 1개 | — |
| 작업실·비교·올리기·로그인·관리자 | 없음 | 글 쓰는 사람을 방해하지 않음 |

## 화면 구성

MVP 화면은 10개다. 주소는 사람이 읽을 수 있게 작품 슬러그를 쓴다.

| 화면 | 주소 | 핵심 요소 |
| --- | --- | --- |
| 홈 | `/` | 새 원작, 갈래가 많이 나는 원작, 별 많은 갈래 카드 |
| 로그인·필명 설정 | `/login`, `/onboarding` | 구글 버튼, 필명 중복 확인 |
| 작품 대문 | `/w/[작품]` | 제목, 작가, 계보 줄, 소개, 라이선스, 별, 장 목록(물려받음/고침/새 장 표시), 탭: 목차 · 갈래 지도 |
| 장 읽기 | `/w/[작품]/[장번호]` | 본문, 이전·다음, 글자 크기, 끝에 '여기서 갈라지기'와 '이 장에서 갈라진 갈래 N개' |
| 갈래 지도 | `/w/[작품]/tree` | 장 축 위 나무 그림, 가지 눌러 이동 |
| 갈래 만들기 | 모달 | 갈래 제목, 한 줄 소개, 라이선스 확인(원작과 같은 조건 자동 적용) |
| 작업실 | `/w/[작품]/edit` | 왜쪽 장 목록(끌어서 순서 변경), 가운데 편집기, 저장·메모, 수정 기록 |
| 비교 | `/w/[작품]/[장번호]/compare` | 원작·갈래 나란히, 바뀐 문장 색 표시 |
| 새 작품 올리기 | `/new` | MD 업로드·붙여넣기 → 장 분할 미리보기 → 정보 입력 → 공개 |
| 프로필 | `/@[필명]` | 내 원작, 내 갈래, 받은 별, 알림 |

광고가 들어갈 자리는 F10 표대로 처음부터 레이아웃에 잡아 둔다. 관리자 화면(`/admin`)은 신고 목록과 숨김·복구만 둔다.

디자인 방향은 '읽기 좋은 종이책'이다. 본문은 한글 명조 계열, 넓은 행간, 한 줄 40자 내외로 두고, 갈래 지도만 화려하게 만든다.

## 데이터 모델

테이블 7개와 뷰 1개다. 핵심은 `chapters`가 본문을 갖지 않고 `revisions`의 한 수정본을 가리킨다는 점이다. 갈래를 만들 때는 원작 장이 가리키던 수정본 id만 복사하므로, 본문은 한 번도 복제되지 않는다.

| 테이블 | 담는 것 | 핵심 컬럼 |
| --- | --- | --- |
| profiles | 사용자 | id(=auth.users), handle, display\_name, bio, is\_admin |
| works | 원작과 갈래 모두 | owner\_id, slug, title, summary, license, allow\_fork, ai\_usage, parent\_work\_id, root\_work\_id, fork\_chapter\_position, fork\_note, is\_canon, visibility, star\_count, fork\_count |
| chapters | 작품의 장 | work\_id, position, title, head\_revision\_id, origin\_revision\_id, state(inherited/modified/new) |
| revisions | 장의 수정본(변경 불가) | chapter\_id(처음 만든 장), author\_id, title, body\_md, parent\_revision\_id, message, created\_at |
| stars | 별 | user\_id, work\_id (함께 기본키) |
| notifications | 알림 | user\_id, kind(fork/star/canon), work\_id, actor\_id, read\_at |
| reports | 신고 | reporter\_id, work\_id, chapter\_id, reason, detail, status |
| — | (뷰) work\_lineage | 재귀 쿼리로 뿌리까지의 계보를 돌려주는 뷰 |

```sql
-- 핵심 3개 테이블 초안 (Supabase Postgres)
create table works (
  id uuid primary key default gen_random_uuid(),
  owner_id uuid not null references profiles(id),
  slug text unique not null,
  title text not null,
  summary text,
  -- 장르 칼럼 없음(웹소설 전반)
  license text not null default 'CC-BY-SA-4.0',
  allow_fork boolean not null default true,
  ai_usage text not null default 'none',      -- none | partial | mostly
  parent_work_id uuid references works(id),   -- 원작이면 null
  root_work_id uuid references works(id),     -- 원작이면 자기 자신
  fork_chapter_position int,                  -- 갈림점(장 번호)
  fork_note text,                             -- 한 줄 갈래 소개
  is_canon boolean not null default false,
  visibility text not null default 'draft',   -- draft | public | hidden
  star_count int not null default 0,
  fork_count int not null default 0,
  created_at timestamptz default now()
);

create table revisions (
  id uuid primary key default gen_random_uuid(),
  chapter_id uuid not null,                   -- 처음 만든 장
  author_id uuid not null references profiles(id),
  title text not null,
  body_md text not null,
  parent_revision_id uuid references revisions(id),
  message text,
  created_at timestamptz default now()
);

create table chapters (
  id uuid primary key default gen_random_uuid(),
  work_id uuid not null references works(id) on delete cascade,
  position int not null,
  head_revision_id uuid not null references revisions(id),
  origin_revision_id uuid references revisions(id), -- 갈래가 물려받은 원작 수정본
  state text not null default 'new',          -- inherited | modified | new
  unique (work_id, position)
);
```

갈래 만들기는 데이터베이스 함수 `fork_work(source_work_id, at_position, title, note, requested_slug)` 하나로 처리한다. 함수 안에서 works 한 줄을 만들고, 1\~N장의 chapters를 같은 head\_revision\_id로 복사하고(1\~N−1은 inherited, N은 modified 대기), 원작의 fork\_count를 올린다. 원작자 알림은 fork\_work가 아니라 갈래가 처음 공개될 때 넣는다(F8). 한 트랜잭션이라 중간에 실패해도 반쯤 갈래가 남지 않는다.

권한은 Supabase RLS(행 단위 보안)로 건다. 공개 작품은 누구나 읽고, 작품·장·수정본 쓰기는 owner만, revisions는 누구도 수정·삭제할 수 없다(새로 쌓기만). is\_canon은 뿌리 원작자만 바꾼다.

**2단계에서 다음 단계로 넘긴 일**

- [x] (4단계) 갈림점 자동 갱신: 물려받은 장을 고치거나 지우거나 옮기면, 또는 그 앞에 새 장을 넣으면 `fork_chapter_position`을 '처음으로 달라진 장'으로 당긴다(`chapters_track_fork_point` 트리거). 갈림점은 당겨지기만 한다.
- [x] (4단계) 장 저장 함수: `save_chapter()`가 수정본 쌓기와 head 옮기기를 한 번에 한다. 편집을 시작한 head(base)가 그 사이 바뀌었으면 덮어쓰지 않고 거절한다. 되돌리기(`revert_chapter()`)도 이전 내용으로 새 수정본을 쌓는다. 장 추가·삭제·순서 변경도 함수로만 하고, 장과 수정본에 대한 직접 쓰기 권한은 거뒀다.
- [x] (4단계) 갈래 공개 때 원작자 알림: `fork_work` 안의 알림을 빼고, 갈래가 처음 공개될 때(`first_published_at`이 채워질 때) 부모 작가에게 한 번만 넣는다. 자기 작품에서 갈라진 갈래는 알리지 않는다.
- [x] (4단계) 갈래 주소: 갈래 만들기 창에서 제목을 로마자로 바꿔 주소를 채우고 고칠 수 있게 했다(겹치면 -2, 저장 전 최종 주소 표시). 임시 저장 동안 대문에서 바꿀 수 있고 공개 뒤에는 잠긴다.
- [x] (4단계, 추가) 작품 지우기: 한 번도 공개하지 않았고 갈래도 없는 작품(원작·갈래)은 작가가 `delete_work()`로 지운다. 수정본은 쌓기만 하는 규칙대로 남긴다.
- [x] (6단계) 작품 대문의 갈래 수는 공개된 갈래만 센다. `fork_count`는 이제 '공개된 직접 갈래 수'이고 `works_maintain_fork_count` 트리거가 공개·비공개·숨김 전환 때 맞춘다(`fork_work`·`delete_work`는 더 이상 직접 세지 않는다).
- [x] (6단계) 두 번째 계정으로 갈라지기·알림 흐름 직접 확인: 『칼의 여행』 8장에서 갈라져 8장을 고치고 9~11장을 쓴 뒤 공개하면, 원작자의 알림 화면에 알림이 뜨고 갈래 대문에 계보가 보인다(4단계 완료 기준을 알림 화면과 함께 확인). 별 알림, 정사 배지와 지도 강조, 신고→숨김→복구 흐름까지 두 계정으로 확인했다.
- [x] (6단계) 관리자 숨김 함수: `admin_hide_work()`·`admin_restore_work()`가 `is_admin()`을 확인한다. 숨기기 직전 상태를 `hidden_from`에 적어 두고 복구 때 그 상태로 돌린다. 숨기면 열린 신고를 처리됨으로 닫고, 숨김·복구 모두 작가에게 알린다(관리자 이름은 남기지 않음).
- [x] (6단계, 추가) 숨겨진 작품: 작가·관리자만 읽고 다른 사람에게는 404. 작가에게는 "관리자에 의해 숨겨진 작품입니다" 안내. 다른 작품의 계보에는 자리를 남기고 제목·작가 없이 '숨겨진 작품'으로 표시하며, 그 작품의 갈래는 그대로 둔다.
- [x] (6단계, 추가) 신고는 관리자만 읽는다(신고자 본인·작가도 못 읽음). 같은 사람이 같은 작품·장에 열린 신고를 두 번 넣지 못한다.
- [ ] (7단계) 출시 점검: `npm run seed:forks -- --reset` 실행. 5단계의 개발용 시드 원작(`dev-seed-original`)·갈래 5개와 시드 사용자(seed-*@forkfiction.test)가 운영 DB에 있으므로 출시 전에 지운다.

## 기술 스택과 구조

Next.js + Supabase + Vercel 조합을 쓴다. Supabase 구글 로그인은 빵심닷컴에서 이미 써 본 구성이고, 세 서비스 모두 초기에는 무료 요금제로 충분하다. 별도 백엔드 서버 없이 Next.js 서버 컴포넌트·서버 액션과 Supabase 함수로 끝낸다.

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 프레임워크 | Next.js(App Router) + TypeScript | 서버 렌더링으로 장 페이지가 검색에 잡힘, Claude Code가 가장 능숙하게 다루는 스택 |
| 스타일 | Tailwind CSS + shadcn/ui | 화면을 빠르게 만들고 고치기 쉬움 |
| DB·로그인 | Supabase(Postgres, Auth 구글, RLS) | 포크 함수를 DB 함수로 두고 권한을 RLS로 관리 |
| MD 렌더링 | react-markdown + remark-gfm + rehype-sanitize | 사용자 글에 스크립트가 섬여도 실행되지 않게 걸러냄 |
| 편집기 | CodeMirror 6(마크다운 모드) | 긴 글도 가볍고 한글 입력이 안정적 |
| 비교 | jsdiff(문단·문장 단위) | 글자 단위보다 소설 읽기에 맞는 비교 |
| 갈래 지도 | React Flow(@xyflow/react) + 자체 배치 | 나무 그림을 누르고 끌고 확대할 수 있음 |
| 배포 | Vercel | GitHub에 올리면 자동 배포, 미리보기 주소 |
| 테스트 | Vitest(함수), Playwright(화면 흐름) | Claude Code가 스스로 돌려 보며 고칠 수 있음 |

비용 메모: 도메인 연 2만 원 안팎만 있으면 시작할 수 있다. 사용자가 늘어 Supabase·Vercel 무료 한도를 넘기면 유료 요금제로 옮긴다(요금은 출시 전 각 사이트에서 확인).

## 라이선스·운영 정책

기본 라이선스는 CC BY-SA 4.0(출처 표시, 동일 조건 변경 허락)이다. "누구나 갈라져 나갈 수 있되, 출처를 밝히고 갈래도 같은 조건으로 열어 둔다"는 서비스의 방식과 그대로 맞는다.

| 선택지 | 갈래 허용 | 상업적 이용 | 쓰임 |
| --- | --- | --- | --- |
| CC BY-SA 4.0 (기본) | 예 | 허용 | 가장 열린 선택 |
| CC BY-NC-SA 4.0 | 예 | 금지 | "내 이야기로 다른 사람이 돈을 버는 건 싫다"는 원작자용 |
| 갈래 금지(모든 권리 보유) | 아니오 | — | 읽기만 가능. 갈래 버튼이 숨겨짐 |

- 갈래는 원작의 라이선스를 그대로 물려받고 바꿀 수 없다(SA 조건).
- 원작자가 나중에 '갈래 금지'로 바꿔도 이미 나온 갈래는 유지된다. CC 라이선스는 한 번 허락하면 되돌릴 수 없기 때문이다. 작품을 공개할 때 이 점을 한 번 더 알려 준다.
- 계보 표기는 라이선스의 출처 표시 조건을 대신하므로 갈래 작가가 지울 수 없다.
- AI 활용 표기: 올릴 때 '없음 / 일부 / 대부분' 중 하나를 고르고 작품 대문에 표시한다. AI로 쓴 글을 막지는 않되 독자가 알고 고를 수 있게 한다.
- 남의 작품을 자기 원작인 척 올리는 것은 금지한다. 올리기 화면에 "이 작품을 올릴 권리가 있습니다" 확인 체크를 두고, 표절 신고가 들어오면 관리자가 확인 후 숨긴다.
- 출시 전에 이용약관과 개인정보 처리방침을 만든다. 로그인 정보(구글 이메일)를 모으므로 처리방침은 필수다. 부가통신사업 신고 등 운영자 의무는 서비스 규모와 수익화 여부에 따라 달라지므로 공개 전에 전문가에게 확인한다.
- 『칼의 여행』을 첫 원작으로 올릴 때는 AI 활용 '대부분', 라이선스 CC BY-SA 4.0을 권장한다. 원작자가 무엇을 기획했는지는 작품 소개에 적는다.

광고와 라이선스가 부딪히는 지점이 하나 있다. 원작자가 CC BY-NC-SA(비영리)를 골랐는데 그 작품 옆에 광고를 붙이면, 플랫폼의 영리 이용으로 볼 여지가 있다. 그래서 약관에 "작품을 올리면, 선택한 라이선스와 별도로 플랫폼이 그 작품을 게시하고 광고와 함께 보여 줄 수 있도록 허락한다"는 조항을 넣는다. 기본값 CC BY-SA 4.0은 상업적 이용을 허용하므로 이 문제가 없다. 약관 문구는 출시 전 전문가 검토를 받는다.

## Claude Code 개발 로드맵

개발은 8단계로 나누고, 한 단계가 끝날 때마다 직접 화면을 눌러 보고 커밋한 뒤 다음으로 넘어간다. 한 번에 "다 만들어줘"라고 하면 Claude Code가 크게 만들고 크게 틀린다. 작게 나눠 시키고, 각 단계 첫 메시지는 플랜 모드(Shift+Tab 두 번)로 계획부터 받아 확인하는 것이 요령이다.

**운영 요령**

- 이 기획서를 `docs/PLAN.md`로 저장소에 넣고, 아래 CLAUDE.md를 루트에 둔다. Claude Code는 매 대화 시작마다 CLAUDE.md를 읽는다.
- 단계마다 새 대화(`/clear`)로 시작하면 이전 단계의 잡다한 맥락이 섞이지 않는다.
- 비밀 키(Supabase service role 키 등)는 `.env.local`에만 두고, 채팅에 붙여 넣지 않는다.
- 막히면 에러 메시지를 그대로 붙여 넣고 "원인부터 설명하고 고쳐줘"라고 한다.

**단계별 첫 프롬프트**

0단계 — 준비 (Supabase·Google Cloud·Vercel 계정 작업은 직접 하고, 키를 .env.local에 넣은 뒤)

```text
docs/PLAN.md는 우리가 만들 'ForkFiction(포크픽션)' 서비스의 기획서야. 먼저 전부 읽고 이해한 내용을 다섯 줄로 요약해줘.
그다음 Next.js(App Router, TypeScript) + Tailwind + shadcn/ui 프로젝트를 만들고,
Supabase 클라이언트(@supabase/ssr)를 서버·브라우저용으로 설정해줘. 환경 변수는 .env.local에 있어.
아직 기능은 만들지 말고, 홈에 'ForkFiction' 글자만 뜨게 해. npm run build가 통과하는지 확인해줘.
```

1단계 — 로그인

```text
PLAN.md의 F1을 구현하자. Supabase Auth 구글 로그인, profiles 테이블(마이그레이션 파일로),
첫 로그인 때 /onboarding에서 필명과 표시 이름을 받는 흐름, 헤더의 로그인/내 프로필 메뉴까지.
필명은 영문 소문자·숫자·밑줄 3~20자, 중복 불가. 먼저 계획을 보여주고 내가 승인하면 만들어.
```

2단계 — DB

```text
PLAN.md의 '데이터 모델'대로 나머지 테이블을 마이그레이션으로 만들어줘.
꼭 지킬 것: revisions는 insert만 가능(update/delete 금지), 갈래는 fork_work() DB 함수 하나로 트랜잭션 처리,
is_canon은 뿌리 원작자만 변경. 모든 테이블에 RLS를 켜고 정책을 써줘.
RLS와 fork_work를 검증하는 테스트도 만들어서 돌려 봐. 마지막으로 seed/kalui-yeohaeng.md를 읽어
원작 하나로 넣는 시드 스크립트를 만들어줘.
```

3단계 — 올리기·읽기

```text
PLAN.md의 F2와 '화면 구성'의 /new, 작품 대문, 장 읽기를 만들자.
장 분할 규칙은 PLAN.md 그대로고, 분할 함수는 따로 빼서 Vitest 테스트를 먼저 쓴 다음 구현해.
MD 렌더링은 react-markdown + remark-gfm + rehype-sanitize. 본문은 한글 명조, 한 줄 40자 내외, 넓은 행간.
광고 자리는 PLAN.md F10대로 AdSlot 컴포넌트를 만들어 회색 자리표시로 넣어줘(실제 광고 코드는 아직 없음). 완료되면 seed의 『칼의 여행』이 1~10장으로 읽히는지 확인해줘.
```

4단계 — 갈라지기·작업실

```text
PLAN.md의 F3, F4를 구현하자. 서비스의 핵심이니 규칙을 하나씩 테스트로 먼저 적고 시작해.
- N장에서 갈라지면 1~N-1장은 inherited, N장은 고칠 초안, N+1 이후는 없음
- inherited 장을 고치면 modified로 바뀌고 갈림점이 갱신됨
- 저장할 때마다 revisions에 새 수정본, 되돌리기 가능
- 계보 줄은 work_lineage 뷰로 만들고 모든 갈래 대문에 표시
편집기는 CodeMirror 6 마크다운 모드, 오른쪽에 미리보기, 모바일에서는 탭 전환.
```

5단계 — 비교·갈래 지도

```text
PLAN.md의 F5, F6을 만들자. 비교는 jsdiff로 문단 단위 나란히 보기, 비교 대상은 origin_revision_id.
갈래 지도는 @xyflow/react로, 가로축을 장 번호로 두고 원작을 굵은 줄, 갈래를 갈림점에서 뻗는 가지로 그려줘.
배치 계산은 순수 함수로 빼서 테스트해. 테스트용으로 갈래 5개(갈래의 갈래 1개 포함)를 만드는 시드도 추가해줘.
```

6단계 — 반응·운영

```text
PLAN.md의 F7, F8, F9를 구현해줘. star_count·fork_count는 DB 트리거로 유지하고,
알림은 갈래 공개와 별·정사 변경 때 쌓이게 해. /admin은 profiles.is_admin인 사람만 들어갈 수 있게.
```

7단계 — 출시 준비

```text
출시 전 점검을 하자. 모바일 폭 375px에서 모든 화면을 확인하고, Playwright로
'로그인 → 올리기 → 다른 계정으로 갈라지기 → 고치기 → 비교 → 갈래 지도' 흐름 테스트를 만들어 돌려줘.
약관·개인정보 처리방침 페이지 틀, 작품·장 페이지 메타태그(제목·소개), 404·에러 페이지도 만들어.
마지막으로 보안 점검: RLS 빠진 테이블, 클라이언트에 노출된 비밀 키, 사용자 MD의 스크립트 실행 여부를 확인해줘.
```

**CLAUDE.md 초안**

```markdown
# ForkFiction (포크픽션)
포크할 수 있는 소설 플랫폼. 기획은 docs/PLAN.md가 기준이다. 기획과 다르게 해야 하면 먼저 물어볼 것.

## 스택
- Next.js App Router + TypeScript(strict), Tailwind, shadcn/ui
- Supabase(Postgres, Auth Google, RLS). 클라이언트는 @supabase/ssr
- 테스트: Vitest(단위), Playwright(흐름)

## 명령어
- npm run dev / npm run build / npm test / npx playwright test
- DB 변경은 항상 supabase/migrations/의 새 마이그레이션 파일로. 대시보드에서 직접 고치지 않는다.

## 꼭 지킬 규칙
- revisions는 쌓기만 한다. 수정·삭제 코드를 만들지 않는다.
- 갈래 생성은 fork_work() DB 함수로만 한다.
- 새 갈래 알림은 갈래를 만들 때가 아니라 처음 공개될 때 원작자에게 보낸다.
- 계보 표기는 어떤 화면에서도 숨기거나 지울 수 없다.
- 사용자 MD는 반드시 rehype-sanitize를 거쳐 렌더링한다.
- service role 키는 서버 코드에서만 쓴다.
- 광고는 AdSlot 컴포넌트로만 넣는다. 작업실·비교·올리기·로그인·관리자 화면에는 넣지 않는다.
- 장르 구분은 만들지 않는다.
- 화면 문구는 한국어. 용어: 원작, 갈래, 갈림점, 계보, 갈래 지도, 정사, 별

## 일하는 방식
- 큰 작업은 계획부터 보여주고 승인받는다.
- 규칙이 있는 로직(장 분할, 포크, 갈래 지도 배치)은 테스트를 먼저 쓴다.
- 끝나면 npm run build와 npm test를 돌리고 결과를 알려준다.
```
